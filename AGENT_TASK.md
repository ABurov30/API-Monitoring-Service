# API Monitoring Service — задание для coding-агента

## Цель и порядок работы

Реализуй полноценное тестовое fullstack-приложение: Spring Boot периодически опрашивает публичный API курсов валют, сохраняет результаты в PostgreSQL и публикует события в Kafka через Transactional Outbox. Vue-приложение предоставляет вход, dashboard и CRUD с разграничением доступа.

Документ самодостаточен: исходное задание и решения заказчика собраны ниже. Источник требований — «Тестовое задание на позицию Fullstack разработчик», согласование решений от 14.10.2026.

Сначала изучи существующий репозиторий и действующие инструкции. Для пустого проекта создай структуру с каталогами `backend/`, `frontend/`, `docs/` и корневым `README.md`. Составь короткий план, затем реализуй приложение, проверь его запуск и исправь найденные ошибки. Заверши работу описанием результата и фактически выполненных проверок.

Не ограничивайся каркасом, заглушками или планом. Для тестов используй управляемые заглушки внешнего HTTP API, а рабочее приложение подключи к реальному источнику. Существенные отклонения от этого документа явно объясняй.

## 2. Принятые технические допущения

Следующие решения конкретизируют недостающие детали ТЗ. Они являются рабочими настройками этого задания, а не дополнительными пожеланиями заказчика:

- Один экземпляр backend в базовом Docker Compose; один экземпляр PostgreSQL и Kafka.
- Frontend: TypeScript, Composition API, Pinia для состояния авторизации, Element Plus для UI.
- Источник: Frankfurter v2, базовая валюта EUR, котируемые валюты USD, GBP и CHF.
- `GET /data` возвращает последние 10 записей и общее количество записей.
- Dashboard USER показывает только доступность сервиса; данные и их количество доступны ADMIN.
- Ручные CRUD-операции изменяют записи в БД. Kafka-события создаются только по результатам планового опроса.
- Access token действует 15 минут, refresh token — до 7 дней; значения настраиваются.
- Автоматическая отправка одного outbox-события ограничена 20 попытками; затем событие сохраняется в состоянии FAILED для явного перезапуска.
- Порог покрытия: не менее 80% строк и 80% ветвей backend и frontend.
- Базовая сдача содержит ручной сценарий проверки интерфейса. Пагинация, поиск и автоматизированные браузерные E2E-тесты не входят в согласованный объём.
- Один backend и один frontend достаточны. Kafka consumer, отдельные микросервисы, Redis и Kubernetes для выполнения этого задания не требуются.

Точные patch-версии зависимостей и Docker-образов выбери совместимыми с Java 17 и Spring Boot 3.x. Зафиксируй их, добавь Maven Wrapper и frontend lockfile. Проверь документацию выбранных версий; не переноси примеры Spring Boot 4 / Spring Framework 7 без проверки совместимости.

## 3. Источник данных и плановый опрос

Рабочий endpoint:

```text
https://api.frankfurter.dev/v2/rates?base=EUR&quotes=USD,GBP,CHF
```

Документация: https://frankfurter.dev/

При подготовке этого задания 14.10.2026 endpoint проверен прямым HTTP-запросом: получен HTTP 200 и JSON-массив курсов с полями `date`, `base`, `quote`, `rate`. Это проверка доступности на момент подготовки, а не гарантия будущей доступности.

Frankfurter не требует API-ключа; курсы обновляются ежедневно. Опрос раз в минуту нужен для демонстрации мониторинга по ТЗ. Повторяющийся payload является нормальным результатом нового опроса и сохраняется отдельной записью.

### Последовательность одного опроса

1. Scheduler запускает один цикл опроса.
2. HTTP-клиент выполняет запрос с таймаутами и ограничением размера ответа.
3. При временной ошибке Spring Retry повторяет только внешний HTTP-запрос.
4. После успеха или окончательной ошибки формируется один итоговый результат.
5. В одной короткой транзакции сохраняются `ApiDataEntity` и outbox-событие.
6. Транзакция завершается; отдельный publisher доставляет событие в Kafka.

HTTP-запросы, ожидание backoff и отправка в Kafka выполняются вне транзакций PostgreSQL. Временные ошибки отдельных попыток не создают отдельные записи: на завершившийся цикл приходится одна итоговая запись и одно событие, если транзакция успешно закоммичена.

Успех — HTTP 2xx с корректным ожидаемым JSON. В `payload` сохраняй исходное тело ответа как строку. Некорректный JSON, пустой ответ вместо данных и превышение лимита тела оформляй как окончательную ошибку опроса.

При окончательной ошибке сохраняй `success=false` и понятное безопасное описание ошибки: категория, HTTP-статус при наличии, число фактических попыток. Не включай stack trace, токены и внутренние секреты в payload.

Ошибка записи в БД не является ошибкой внешнего API: не отправляй событие до commit и не пытайся представить сбой БД как успешно сохранённый результат. Зафиксируй сбой в журнале; следующий плановый цикл продолжает работу.

### Расписание и retry

- Используй `@Scheduled` с cron по умолчанию `0 * * * * *` и явно заданной зоной UTC.
- Запуски одного poller внутри одного JVM не перекрываются. Если предыдущий цикл ещё выполняется, новый запуск пропускается, без накопления очереди.
- Poller и outbox publisher не должны блокировать друг друга одним scheduler-потоком.
- Используй именно библиотеку Spring Retry: `RetryTemplate` либо корректно проксируемый `@Retryable`.
- Для `@Retryable` исключи self-invocation: вызов должен проходить через Spring proxy.
- `maxAttempts=3` означает первый запрос и максимум два повтора.
- Базовые задержки: 1 секунда, затем 2 секунды; multiplier = 2, максимальная обычная задержка = 30 секунд.
- Повторяй сетевые ошибки, таймауты, HTTP 408, 429 и 5xx.
- Остальные 4xx, ошибки десериализации и превышение лимита ответа завершают цикл без повторов.
- Для 429 учитывай корректный `Retry-After` в секундах или HTTP-date. Следующий запрос не должен происходить раньше указанного момента.
- Если Retry-After не помещается в бюджет текущего цикла, заверши его ошибкой и отложи последующие плановые обращения к источнику до разрешённого времени.
- При отсутствующем или некорректном Retry-After используй обычный backoff.
- По исчерпании попыток сохраняй окончательную ошибку и событие `api-errors`.
- Не накладывай незаметно дополнительные HTTP retry поверх Spring Retry.

Расписание, URL, connect/read/общий timeout, размер ответа, maxAttempts и backoff должны настраиваться через валидируемые `@ConfigurationProperties`. В тестовом профиле плановый опрос выключается.

## 4. Данные и миграции

### ApiDataEntity

| Поле | Представление | Правила |
| --- | --- | --- |
| id | UUID / UUID | Генерируется сервером |
| createdAt | Instant / timestamptz | Время создания записи, UTC, неизменяемое |
| success | boolean / boolean | Итог опроса или значение ручной записи |
| payload | String / text | Исходный ответ API либо сообщение об ошибке |

Таблица `api_data`. Добавь индекс для выборки `created_at DESC, id DESC`.

В POST и PUT клиент передаёт только `success` и `payload`. Оба поля обязательны; `success=false` является допустимым значением. Payload — непустая строка до 65 536 байт UTF-8. PUT заменяет оба изменяемых поля, а id и createdAt сохраняются. Управляемые сервером поля в запросе отклоняй как ошибку валидации.

Payload по контракту является строкой, поэтому ручной ввод не обязан быть JSON. Интерфейс может форматировать валидный JSON для просмотра и показывать обычный текст в остальных случаях.

### Остальные таблицы

Через Liquibase создай:

- `api_data`;
- `api_outbox`;
- `users` и хранение ролей;
- `refresh_tokens`, необходимые ограничения и индексы.

Включи `spring.jpa.hibernate.ddl-auto=validate`. Проверяй миграции на настоящем PostgreSQL; H2 не является заменой интеграционным тестам выбранной БД.

Минимальные поля outbox:

- `id` — UUID, одновременно eventId;
- `data_id` — id исходной записи;
- `topic`, `event_payload` — неизменяемый снимок события;
- `status` — PENDING, IN_PROGRESS, SENT, FAILED;
- `attempts`, `next_attempt_at`;
- `locked_until`, `lock_token`;
- `created_at`, `sent_at`, `last_error`.

Добавь индекс для выбора готовых к отправке событий. Редактирование или удаление ApiDataEntity не изменяет и не удаляет уже созданный outbox-снимок. Не используй каскадное удаление outbox при удалении данных.

## 5. Transactional Outbox и Kafka

### Формат события

Оба топика используют один JSON-контракт, например:

```json
{
  "schemaVersion": 1,
  "eventId": "c6ba1db0-e734-4d08-97fd-17b61b083b34",
  "dataId": "70c07604-2875-49e5-8e2d-1d912b87ff37",
  "occurredAt": "2026-10-14T12:30:00Z",
  "success": true,
  "payload": "[{\"date\":\"2026-10-14\",\"base\":\"EUR\",\"quote\":\"USD\",\"rate\":1.1202}]"
}
```

Числа и время в примере иллюстрируют формат, а не являются фикстурой актуальных курсов.

- Kafka key: `dataId`.
- `success=true` направляется в `api-data`, `success=false` — в `api-errors`.
- `eventId` и снимок payload сохраняются при всех повторных отправках.
- Сбой Kafka не меняет результат внешнего HTTP-опроса и не порождает новое событие `api-errors`.
- Consumer для демонстрации не обязателен; README должен содержать команды чтения обоих топиков.

### Работа publisher

1. Короткой транзакцией выбери готовую запись через `SELECT ... FOR UPDATE SKIP LOCKED`.
2. Учитывай PENDING с наступившим `next_attempt_at` и IN_PROGRESS с истёкшим lease.
3. Если лимит попыток исчерпан, переведи запись в FAILED.
4. Иначе увеличь `attempts`, назначь новый `lock_token`, установи IN_PROGRESS и `locked_until`, затем commit.
5. Вне транзакции отправь сообщение и дождись подтверждения Kafka с ограниченным timeout.
6. При подтверждении короткой транзакцией установи SENT и `sent_at`.
7. При ошибке назначь следующую попытку с exponential backoff; при достижении лимита установи FAILED.
8. Обновляй результат только при совпадении текущего `lock_token` и статуса IN_PROGRESS, чтобы запоздавший worker не перезаписал решение нового владельца.

Увеличение attempts при захвате делает лимит применимым и к падениям worker. Не держи блокировку PostgreSQL во время сетевой отправки.

Для простоты один publisher обрабатывает сообщения последовательно. За один тик можно обработать до 10 сообщений, но захватывать по одному непосредственно перед отправкой, чтобы lease не истекал в очереди локальной пачки.

Значения по умолчанию:

- Интервал publisher — 1 секунда.
- Максимум 20 попыток на событие.
- Backoff начинается с 5 секунд, multiplier = 2, предел = 5 минут.
- Lease = 60 секунд.
- Kafka producer: `acks=all`, `enable.idempotence=true`.
- Ограничь `max.block.ms`, `request.timeout.ms`, `delivery.timeout.ms` и ожидание результата отправки. Совокупное максимальное ожидание должно быть меньше lease с запасом.
- Все значения настраиваемые; проверь их взаимную совместимость.

После перезапуска приложения незавершённые события остаются в БД и могут быть подобраны после истечения lease. FAILED не удаляется: добавь документированную служебную команду или SQL-процедуру для явного повторного запуска выбранного события после устранения причины. При replay сохраняй eventId.

В README честно опиши семантику доставки: возможна повторная публикация после успешного приёма Kafka и падения до отметки SENT. Idempotent producer не даёт сквозного exactly-once между PostgreSQL и Kafka. EventId позволяет будущим потребителям устранять дубликаты. При конечном лимите retry доставка после длительного сбоя требует replay; бесконечную автоматическую доставку не обещай.

Outbox допускает конкурирующих publisher. Плановый опрос рассчитан на один backend: запуск нескольких backend без отдельной координации приведёт к нескольким опросам за минуту. Укажи это ограничение, не добавляя распределённый scheduler в базовый объём.

## 6. REST API

Пути ниже указаны относительно backend API root.

| Метод | URI | Доступ | Ответ |
| --- | --- | --- | --- |
| GET | /status | USER, ADMIN | 200, краткий статус сервиса |
| GET | /data | ADMIN | 200, последние 10 записей и total |
| GET | /data/{id} | ADMIN | 200 либо 404 |
| POST | /data | ADMIN | 201, созданная запись, Location |
| PUT | /data/{id} | ADMIN | 200, обновлённая запись либо 404 |
| DELETE | /data/{id} | ADMIN | 204 либо 404 |

`GET /data`:

```json
{
  "items": [],
  "total": 0
}
```

Сортировка фиксирована: `createdAt DESC, id DESC`; максимум 10 элементов. `total` — количество всех записей в `api_data`, включая ручные и ошибочные. Каждая запись в items содержит четыре поля из контракта ApiDataEntity. Дополнительную пагинацию не реализуй.

`GET /status`:

```json
{
  "status": "UP",
  "checkedAt": "2026-10-14T12:30:00Z"
}
```

Этот endpoint подтверждает, что backend обслуживает запросы. Он не сообщает об успехе последнего опроса и не обещает исправность всех зависимостей. Не отдавай через него payload, список данных, счётчики БД, строки подключения или другую административную информацию.

Если UI не получает ответ от backend, показывай недоступность или невозможность определить статус. Ошибка внешнего источника и недоступность Kafka сами по себе не означают, что HTTP backend выключен.

### Ошибки и валидация

Используй DTO и Bean Validation. Централизованный `@RestControllerAdvice` формирует единый JSON ошибки с полями `code`, `message`, `timestamp`, `path` и при необходимости `fieldErrors`.

- 400 — некорректный UUID, JSON, поля и значения.
- 401 — отсутствующий, невалидный или истёкший access token.
- 403 — недостаточная роль либо ошибка CSRF.
- 404 — запись не найдена.
- 413 — превышен общий лимит размера HTTP-запроса.
- 503 — временная недоступность инфраструктуры, необходимой для конкретной операции.
- 500 — непредвиденная серверная ошибка с безопасным сообщением.

Для ошибок Spring Security настрой JSON `AuthenticationEntryPoint` и `AccessDeniedHandler`: исключения security filters не покрываются одним ControllerAdvice.

## 7. Авторизация и refresh

Используй Spring Security и проверенные JWT-компоненты, например Spring OAuth2 Resource Server / Nimbus. Алгоритм подписи явно зафиксируй; для этого проекта достаточно HS256 со случайным секретом не менее 256 бит из окружения. Валидируй подпись, issuer, audience, срок действия. Пароли храни через BCrypt.

Дополнительные служебные endpoints авторизации допустимы для обеих ролей и не расширяют доступ USER к бизнес-данным:

| Метод | URI | Назначение |
| --- | --- | --- |
| GET | /auth/csrf | Получить CSRF-токен до входа |
| POST | /auth/login | Вход по username и password |
| POST | /auth/refresh | Ротация refresh и выдача нового access |
| POST | /auth/logout | Отзыв текущей refresh-сессии и очистка cookie |

Успешные login и refresh возвращают `accessToken`, `tokenType=Bearer`, `expiresIn` в секундах и `user` с id, username и ролями. Refresh передаётся через cookie, не в JSON.

Требования к сессии:

- Access token хранится только в памяти frontend и передаётся как `Authorization: Bearer ...`.
- Refresh token — криптографически случайное непрозрачное значение не менее 32 байт; в БД хранится SHA-256 hash, владелец, время истечения и состояние использования / отзыва.
- Refresh cookie: HttpOnly, SameSite=Lax, host-only, Path=/; Secure включён при HTTPS. Для локального HTTP допускается отдельная dev-настройка.
- При refresh атомарно погашай старый токен и создавай новый. Один старый токен не должен успешно обменяться дважды, в том числе при конкурентных запросах.
- Повтор использованного, отозванного или истёкшего refresh возвращает 401. Документируй выбранную политику отзыва связанных refresh-сессий при обнаружении повторного использования.
- POST logout отзывает текущую refresh-сессию, удаляет cookie с теми же атрибутами пути и возвращает 204. Повторный logout безопасен.
- Очистка refresh не отзывает уже выданный stateless access token мгновенно: его срок ограничен TTL. Зафиксируй это поведение в README.
- При перезагрузке страницы frontend восстанавливает вход через refresh.
- На несколько одновременных 401 frontend выполняет один refresh и повторяет исходные запросы не более одного раза.
- Для 403 refresh не запускается. Ошибка login или refresh не должна создавать бесконечный interceptor-цикл.
- Logout очищает access token, состояние пользователя и данные dashboard. Запоздавшие ответы предыдущей сессии не возвращают эти данные на экран.

Cookie-based refresh требует защиты от CSRF. Настрой защиту auth POST-запросов, включая login / refresh / logout; CSRF-токен получай через /auth/csrf и передавай отдельным заголовком. Cookie CSRF-токена может быть доступна JavaScript; refresh cookie — нет. Проверь bootstrap до входа, обновление CSRF после изменения сессии и работу Axios с выбранными именами cookie / header.

CRUD аутентифицируется только Bearer-заголовком, refresh cookie не авторизует /data. При настройке CSRF учитывай эту границу; глобальный `csrf.disable()` при cookie-based refresh не допускается.

Используй deny-by-default правила доступа. Анонимный пользователь не получает бизнес-данные. Роли в UI управляют отображением, но настоящие ограничения проверяются backend.

Создай demo USER и ADMIN только для локального профиля. Укажи способ задания их паролей через окружение; регистрация и управление пользователями в объём не входят. Реальные секреты и .env не коммить.

## 8. Frontend

Используй Vue 3 + TypeScript + Vite + Axios + Vue Router + Pinia + Element Plus. HTTP-вызовы находятся в services, состояние авторизации — в store, обработка 401 и refresh — в одном месте.

Рекомендуемые страницы и компоненты:

- /login: поля входа, валидация, loading, понятная ошибка неверных данных.
- /dashboard: статус backend для обеих ролей.
- Dashboard ADMIN: общее число записей, последние данные и последние 10 записей.
- CRUD ADMIN: просмотр payload, создание и редактирование через форму / диалог, удаление с подтверждением.
- Страница или состояние 403 при попытке открыть административный экран.
- Общий layout: текущий пользователь, роль, выход, переключатель темы.

Поведение:

- USER не вызывает /data и не видит административные кнопки, счётчики или payload.
- Для ADMIN счётчик берётся из total, а не из длины массива items.
- После CRUD обновляются список и счётчик.
- Данные dashboard можно обновлять автоматически раз в минуту и кнопкой «Обновить»; таймеры очищаются при уходе со страницы.
- Покажи отдельные состояния initial loading, empty, success, error и stale data после сбоя обновления.
- Ошибка внешнего опроса отображается как запись success=false; недоступность самого backend — как ошибка соединения.
- Формы блокируют повторную отправку во время запроса и показывают серверные ошибки валидации.
- Payload отображается как текст; не используй v-html для содержимого API.
- Тёмная и светлая темы полноценны для таблиц, форм, диалогов и уведомлений. Выбор темы можно сохранять в localStorage; токены туда не сохраняются.
- На ширине около 360 px интерфейс остаётся рабочим: таблица имеет управляемую прокрутку или компактный вид, диалоги помещаются в экран.
- Кнопки и поля имеют подписи, видимый focus, работают с клавиатуры.
- Короткие пользовательские тексты — на русском.

## 9. Архитектура, конфигурация и эксплуатация

Backend раздели на controller, service, repository, entity, dto, config, security, kafka, scheduler, exception. Конструкторное внедрение зависимостей; транзакционные границы находятся в сервисах. Entity не отдаётся напрямую наружу.

Frontend раздели на components, views, services, router, store, layouts. Сохраняй компоненты небольшими, избегай дублирования HTTP- и auth-логики.

Длительности и пороги валидируй на старте. Общий timeout цикла должен ограничивать фактическую продолжительность, включая backoff; не начинай новую попытку, если для неё не осталось времени. Не используй фоновую отмену, которая оставляет бесконтрольный HTTP-запрос после завершения цикла.

Используй SLF4J / Logback. Для опросов логируй идентификатор цикла, номер попытки и итог; для outbox — eventId, попытку и смену состояния. Секреты, Authorization, cookie и полные тела ответов по умолчанию не логируются.

## 10. Docker Compose и запуск

Корневой Compose поднимает:

- PostgreSQL с именованным volume;
- Kafka в KRaft-режиме;
- backend;
- frontend, собранный Vite и обслуживаемый Nginx.

Для локального одиночного брокера настрой replication factor = 1. Явно создай api-data и api-errors. Различай внутренние и внешние advertised listeners; backend внутри Docker обращается к брокеру по имени сервиса.

Добавь multi-stage Dockerfile для backend и frontend, .dockerignore и healthchecks. Backend должен продолжать работать и накапливать outbox при недоступной Kafka, в том числе если Kafka отсутствует во время старта. Создание топиков и первичная инициализация producer не должны делать такой старт невозможным. Недоступная БД при старте допустимо блокирует готовность приложения.

Настрой единый origin для UI:

- Frontend обращается к /api.
- Nginx и Vite proxy снимают префикс /api и направляют запрос в backend.
- На backend остаются пути /status, /data и /auth.
- Refresh и CSRF cookie используют Path=/, чтобы работать через proxy и при документированном прямом обращении.
- При отдельном origin разрешай только явно заданные CORS origins, методы и credentials.

Предоставь .env.example и воспроизводимый способ создать локальные секреты. После подготовки окружения приложение запускается командой:

```bash
docker compose up --build
```

Также опиши отдельный запуск backend через Maven Wrapper и frontend через npm. Проверь сборку на Java 17 и Docker-образы, доступные для arm64 и amd64.

## 11. Тесты и CI

### Backend

JUnit 5, Mockito где уместно, Spring Boot Test, Testcontainers PostgreSQL и Kafka. Внешний API подменяй WireMock или MockWebServer.

Проверь существенные сценарии:

1. Успешный HTTP-опрос создаёт одну запись success=true и одно событие api-data.
2. Две временные ошибки и успех на третьей попытке: ровно три HTTP-вызова, одна итоговая запись.
3. Три временные ошибки: максимум три HTTP-вызова, одна запись success=false и событие api-errors.
4. Неповторяемая 4xx и некорректный JSON: один вызов и корректная итоговая ошибка.
5. 429: Retry-After соблюдается; большой Retry-After не приводит к преждевременному повтору в следующем cron-тике.
6. Timeout, лимит ответа и общий бюджет цикла реально ограничивают выполнение.
7. Результат опроса и outbox либо коммитятся вместе, либо вместе откатываются.
8. Kafka недоступна: результат остаётся в БД, событие ожидает повтор; после восстановления публикуется.
9. Publisher помечает SENT только после подтверждения Kafka.
10. Истёкший lease, конкурирующий захват и устаревший lock_token обрабатываются корректно.
11. Исчерпание outbox retry переводит событие в FAILED, replay сохраняет eventId.
12. CRUD: DTO, валидация, 201 / 204 / 404, неизменяемые поля, сортировка и максимум 10 элементов при корректном total.
13. Матрица ролей: анонимный / USER / ADMIN для всех бизнес-endpoints.
14. JWT: валидный, истёкший, подменённый, неверный issuer / audience.
15. Refresh: ротация, повтор использованного, истечение, отзыв, конкурентный обмен.
16. CSRF на auth endpoints, cookie-атрибуты и logout.
17. Liquibase поднимает схему с нуля на PostgreSQL.
18. Ручной CRUD не создаёт событий опроса, а удаление данных не удаляет outbox.

Используй управляемые часы / backoff и короткие тестовые настройки вместо реального ожидания минуты. Не делай CI зависимым от публичного Frankfurter API.

### Frontend

Vitest + Vue Test Utils; HTTP-сценарии подменяй на границе клиента.

Проверь:

- Вход и отображение ошибки входа.
- Router guards и различия USER / ADMIN.
- Bootstrap через refresh.
- Несколько одновременных 401 вызывают один refresh; 403 его не вызывает.
- Неудачный refresh завершает сессию без цикла повторов.
- Logout и запоздавший ответ не восстанавливают прежнее состояние.
- Loading, empty, error и stale-состояния dashboard.
- CRUD-формы, подтверждение удаления, обновление счётчика.
- Переключение темы и сохранение настройки.

### Обязательные проверки

Backend:

- Checkstyle;
- Spotless с google-java-format;
- unit tests через Surefire и integration tests через Failsafe;
- JaCoCo с объединённым покрытием unit + integration;
- минимум 80% строк и 80% ветвей.

Frontend:

- ESLint;
- Prettier check;
- vue-tsc;
- Vitest с coverage: минимум 80% строк и 80% ветвей;
- production build.

Не добивайся порога исключением бизнес-логики из coverage. Допустимые исключения — сгенерированные файлы и конфигурация инструментов; перечисли их явно. Тесты должны проверять поведение и ошибки, а не только getters, setters и факт вызова mock.

GitHub Actions запускает проверки на push и pull request. Используй окружение с Docker для Testcontainers. При падении проверок исправляй причину; не отключай правила, тесты или пороги ради зелёного CI.

После логически завершённого изменения запускай соответствующие линтеры и тесты. Перед сдачей выполни полный набор проверок и smoke-сценарий Docker Compose.
