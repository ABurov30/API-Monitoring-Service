# Ручная проверка UI и отказов

После успешного Compose startup:

1. Открыть http://localhost:8081 на ширине 1280px. Убедиться, что до входа видна форма и нет истории.
2. Отправить пустую форму, затем неверный пароль: понятная ошибка; во время запроса повторная отправка заблокирована.
3. Войти как USER. Видны статус, время проверки, роль, тема, выход. Отсутствуют total, payload, список и CRUD. В Network нет `/data`. `/admin` показывает 403.
4. Обновить страницу: вход восстанавливается через CSRF + refresh; токен не появляется в localStorage/sessionStorage. В Application cookies refresh — HttpOnly, Path=/, SameSite=Lax.
5. Выйти, войти ADMIN. Дождаться следующей минуты. Проверить total, последние 10, последнюю запись и раскрытие payload.
6. Создать запись `success=false` с обычным текстом, изменить оба поля. UUID/createdAt сохраняются. Отменить удаление, затем подтвердить. Проверить счётчик и список.
7. Вставить JSON и обычный HTML-текст вроде `<b>text</b>`: содержимое отображается как текст, HTML не выполняется.
8. Переключить светлую/тёмную тему. Проверить таблицу, формы, диалоги и уведомления; перезагрузка сохраняет тему.
9. Повторить на ширине 360px и с клавиатуры: focus видим, таблица прокручивается, диалоги помещаются, поля/кнопки подписаны.
10. Остановить backend (`docker compose stop backend`), нажать Обновить. Видна ошибка соединения, уже полученные записи отмечены устаревшими. Запустить backend и обновить; ошибка исчезает.
11. Выйти во время медленного запроса. Старые payload/пользователь не возвращаются после ответа.
12. Открыть локальный Swagger, выполнить CSRF/login, Authorize, CRUD и logout согласно README.

## Kafka outage

Остановить `kafka`, дождаться планового опроса. Запись api_data сохраняется, outbox остаётся PENDING/IN_PROGRESS. Запустить kafka, дождаться backoff. Убедиться через SQL и console-consumer, что snapshot доставлен и стал SENT. Состояние HTTP backend при этом доступно.

После достижения FAILED выполнить replay выбранного UUID из README. EventId не меняется. Ручное изменение/удаление исходной записи не влияет на snapshot.

## Внешний API

Не используйте нестабильный публичный сервис для автоматизированных тестов. В MockWebServer-сценариях покрыты 503→408→200, исчерпание, 4xx, JSON, таймауты, превышение размера и Retry-After. Для ручного демонстрационного отказа можно временно указать недоступный MONITOR_URL и пересоздать backend: итог должен быть success=false, событие — api-errors.

Скриншоты не приложены: полноценный runtime в текущей среде не запущен. Не выдавайте изображения из подменённых данных за проверку работающего backend.

## Пограничные сценарии сессии

- При задержке login/refresh выйти до прихода ответа: после завершения logout перезагрузка страницы не должна восстанавливать предыдущий вход.
- Задержать один из параллельных ответов 401 до окончания refresh: исходные запросы повторяются по одному разу, второй refresh не отправляется.
- Открыть подтверждение удаления, выйти, затем подтвердить: DELETE не отправляется из прежней сессии.
- Начать создание/редактирование и выйти до ответа: поздний результат не возвращает диалог и не запускает обновление старого dashboard.

Эти сценарии покрыты frontend unit-тестами; браузерная проверка через настоящий backend остаётся обязательной частью ручного прогона.
