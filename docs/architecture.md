# Архитектура и ограничения

## Слои

- controller: HTTP, DTO, коды ответа, cookie.
- service: CRUD, auth-транзакции, HTTP-клиент и retry.
- repository/entity: JPA `ApiDataEntity`, фиксированная сортировка.
- kafka: атомарная запись результата/outbox, claim/ack/retry.
- scheduler: cron UTC и локальная защита от перекрытия.
- security/config/exception: JWT, CSRF, CORS, конфигурация и единые ошибки.

В UI: services — Axios/контракты; store — пользователь и тема; router — доступ; views/components/layouts — представление. Токен не сохраняется в web storage. Единственный общий refresh-promise обслуживает параллельные 401; запоздавший 401 от предыдущей версии токена повторяется с уже обновлённым access без второго refresh. 403 не запускает refresh. Epoch сессии предотвращает принятие старых ответов после logout, включая повтор HTTP-запроса после refresh.

Auth-запросы вместе с получением CSRF выполняются последовательно, чтобы изменения cookie не обгоняли друг друга. Logout очищает UI сразу, дожидается уже отправленного login/refresh и затем отзывает актуальную cookie. Login, оставшийся на стадии CSRF после смены сессии, не отправляет POST. Новая авторизация после начавшегося logout выполняется после него и не очищается его завершением. Подтверждение удаления и завершение CRUD-формы также проверяют сессию и состояние компонента, прежде чем отправить запрос или обновить UI.

## Транзакции

`OutboxStore.saveResult` сохраняет JPA-запись и JDBC-outbox в одной транзакции одного datasource. Snapshot — неизменяемая JSON-строка. createdAt перед сохранением нормализуется до микросекунд PostgreSQL, поэтому POST и последующий PUT возвращают одинаковое время. Foreign key на `data_id` намеренно отсутствует: событие переживает удаление исходной записи.

`claim` выбирает готовое PENDING либо IN_PROGRESS с истёкшим lease, используя SKIP LOCKED. Attempts увеличивается до отправки, поэтому падения процесса тоже расходуют лимит. Новый UUID lock token защищает от старого worker. Ограничение одной записи на захват исключает истечение lease в локальной очереди.

Планировщик имеет 4 потока. Poller и publisher не блокируют друг друга. Cron использует завершение предыдущего вызова и атомарный guard; пропущенные тики не ставятся в очередь. Внутри JVM poller один. Распределённого scheduler нет.

## HTTP и ограничения времени

Apache HttpClient 5 выполняет синхронный запрос без автоматических retry и redirect. Таймер вызывает cancel активного запроса, закрывая transport; отдельной фоновой HTTP-задачи нет. Ограничиваются connect, read, вся попытка, размер распакованного ответа и цикл вместе с backoff. Spring Retry управляет всеми повторами. Новая попытка не стартует, если не остаётся полного request-timeout.

Ожидается массив из трёх положительных курсов EUR→USD/GBP/CHF с корректной ISO-датой. Пустой массив, повтор валюты, некорректный JSON и хвост после JSON — окончательная ошибка. Успешный payload сохраняет исходную строку.

Отсрочка Retry-After хранится в памяти одного poller и теряется при перезапуске процесса. Базовое ТЗ требует соблюдения следующих cron-тиков в работающем JVM; долговременное сохранение rate-limit между перезапусками не реализовано.

## Сессии

Refresh атомарно помечается used под row lock, затем создаётся новый случайный токен. Неудачная транзакция не расходует старый токен. Повтор старого токена возвращает 401, без отзыва других сессий. Это минимальная политика; более строгий family-revocation потребовал бы отдельной модели семейства.

Удалённые/использованные refresh сохраняются для распознавания повторов. Автоматический retention БД и SENT/FAILED outbox не входит в базовый объём; для длительной эксплуатации нужна согласованная политика очистки/архивации.

## Доставка

Подтверждение Kafka предшествует SENT. Между этими действиями возможен crash и дубликат. Producer idempotence действует в Kafka, но не закрывает транзакционный разрыв с PostgreSQL. Для потребителя ключ дедупликации — eventId. После 20 неудач требуется явный replay выбранного FAILED события.

Базовая инфраструктура: один backend, PostgreSQL и Kafka KRaft, replication factor 1. Redis, consumer, Kubernetes, поиск, пагинация, регистрация пользователей и браузерные E2E не добавлены.
